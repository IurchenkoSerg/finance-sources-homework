# Памятка по правилам Codex

Этот файл предназначен для владельца проекта. Это не набор обязательных
instructions для Codex. Он помогает вспомнить, какие сторонние правила могут
замедлять работу, увеличивать расход tokens или конфликтовать с Codex.

## Текущий статус

Адаптированная версия подходящих ECC rules установлена глобально:

```text
~/.codex/AGENTS.md
~/.codex/rules/
```

Глобальный `AGENTS.md` работает как router и требует читать только тематические
файлы, подходящие текущей задаче. Claude-specific команды и безусловные
дорогостоящие требования не переносились. Исходные ECC rules не заменяют
локальные правила конкретного repository.

## Источник

За основу рассматривается набор
[Everything Claude Code: rules](https://github.com/affaan-m/ECC/tree/main/rules),
лицензия MIT, copyright © 2026 Affaan Mustafa.

Набор ECC разработан прежде всего для Claude Code. Перед использованием в
Codex правила необходимо адаптировать. Нельзя слепо копировать Claude settings,
hooks, agents или команды установки.

## Правила с высоким расходом tokens

Следующие инструкции могут увеличить число agent turns, tool calls и общий
расход tokens в несколько раз:

- всегда запускать несколько subagents параллельно;
- использовать `planner`, `architect`, `tdd-guide`, `code-reviewer` и
  `security-reviewer` для каждой задачи;
- проводить несколько раундов анализа с разными ролями;
- выполнять отдельный code review после каждого изменения;
- создавать `PRD`, `architecture`, `system_design`, `tech_doc` и `task_list`
  перед реализацией;
- искать готовую реализацию на GitHub перед каждой новой функцией;
- обязательно применять полный TDD workflow даже для маленьких исправлений.

Рекомендуемая замена: использовать planning и subagents только для сложных,
независимых или рискованных задач. Родительский agent должен собрать результаты
всех запущенных subagents перед завершением ответа.

## Правила, которые замедляют проверки

Эти проверки полезны для production release, но слишком дороги для каждой
небольшой правки:

- обязательное покрытие тестами не менее 80%;
- обязательные Unit, Integration и E2E tests для каждого изменения;
- `npm run build` после редактирования любой строки;
- formatter, linter и type check после каждого изменения файла;
- E2E-проверки одновременно в Chrome, Firefox и Safari;
- screenshots на всех размерах `320`, `375`, `768`, `1024`, `1440` и `1920`;
- Lighthouse и Core Web Vitals audit после каждого UI-изменения;
- проверка light и dark theme после любой правки CSS.

Рекомендуемая замена:

- запускать целевые tests после изменения логики;
- запускать production build после существенных изменений Next.js;
- выполнять полный browser, accessibility и performance audit перед release
  или по отдельному запросу.

## Слишком строгие ограничения

Следующие правила нельзя применять абсолютно во всех ситуациях:

- каждая функция должна быть короче 50 строк;
- каждый файл должен быть короче 800 строк;
- полный запрет `console.log`, включая учебные tests;
- полный запрет mutation даже там, где API или алгоритм её ожидает;
- обязательный `rate limiting` на каждом endpoint;
- обязательный production CSP в любом учебном проекте;
- обязательная сторонняя dependency вместо небольшой локальной функции;
- немедленная остановка всей работы при любом предполагаемом security issue.

Использовать эти значения следует как сигналы для review, а не как безусловные
блокировки.

## Несовместимые с Codex инструкции

Не переносить без адаптации:

- пути `~/.claude/` и файл `~/.claude/settings.json`;
- Claude-specific agents и skills;
- `TodoWrite`;
- Claude-specific `PreToolUse`, `PostToolUse` и `Stop` hooks;
- выбор моделей `Haiku`, `Sonnet` и `Opus`;
- обязательное использование `pnpm`, если project использует другой package
  manager;
- YAML front matter `paths:` как механизм автоматического выбора rules.

Codex автоматически обнаруживает `AGENTS.md` и `AGENTS.override.md`. Остальные
Markdown-файлы применяются только тогда, когда загруженный `AGENTS.md` явно
требует их прочитать.

## Опасные автоматизации

Перед включением обязательно проверить вручную:

- сторонние install scripts;
- hooks, запускающие shell commands;
- удалённый `npx` при каждом редактировании;
- автоматические `commit`, `push`, merge или deployment;
- команды, изменяющие global configuration;
- команды с secrets, токенами или содержимым `.env`;
- destructive Git и filesystem commands.

На момент первоначальной проверки в релевантных ECC rules не было обнаружено
явных инструкций для кражи secrets или удаления пользовательских файлов. Это не
гарантирует безопасность будущих версий repository: перед обновлением правила
нужно проверить повторно.

## Полезные правила, которые стоит сохранить

- KISS, DRY и YAGNI без догматичного применения;
- понятные English identifiers;
- immutable updates там, где они упрощают код;
- validation на границах системы;
- понятная обработка ошибок;
- защита secrets через environment variables;
- semantic HTML, keyboard navigation и accessibility;
- CSS custom properties и responsive design;
- поддержка `prefers-reduced-motion`;
- AAA pattern и понятные названия tests;
- проверка `git status` и diff перед commit;
- Conventional Commits;
- целевые tests и build перед публикацией.

## Что отключать, если Codex стал слишком медленным

Проверять в таком порядке:

1. Убрать обязательное использование нескольких subagents.
2. Убрать code review после каждой маленькой правки.
3. Сделать TDD и 80% coverage условными.
4. Отключить automatic build, browser matrix и Lighthouse.
5. Отключить hooks, запускаемые после каждого редактирования.
6. Убрать обязательный GitHub research перед реализацией.
7. Проверить общий размер `AGENTS.md` и подключаемых файлов.

После изменения global rules необходимо перезапустить Codex session. Project
rules также надёжнее проверять в новой session.

## Как проверить активные инструкции

Из корня проекта можно выполнить:

```bash
codex --ask-for-approval never "Summarize the current instructions."
```

Для проверки конкретной вложенной папки:

```bash
codex --cd app --ask-for-approval never "Show which instruction files are active."
```

## Перед будущим обновлением ECC

1. Проверить новый source commit или release.
2. Просмотреть diff сторонних rules и scripts.
3. Не заменять локальные правила целиком.
4. Переносить только полезные изменения вручную.
5. Проверить ссылки из `AGENTS.md`.
6. Запустить новую Codex session и проверить активные instructions.
7. Если ответы стали значительно длиннее или медленнее, проверить раздел
   «Что отключать, если Codex стал слишком медленным».
